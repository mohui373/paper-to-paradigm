# 论文重组复现产物分级

## 原则

复现产物不是“报告越长越好”，而是让证据、设计、运行、数据和分析能够交接。每项产物必须有明确用途；与当前复现层级无关的文件不强制生成。

## 六层产物

| 层 | 核心产物 | 解决的问题 |
|---|---|---|
| 0. 来源与范围 | DOI/Supplement/OSF/数据/代码账本、版本、访问状态、证据缺口 | 依据来自哪里，哪些材料真的读过 |
| 1. 研究设计 | Study 地图、理论不变量、变量/指标、参与者流程、条件与重复关系 | 到底要保留和检验什么 |
| 2. 实现结构 | 平台清单、Proc/List 或对应对象图、材料清单、随机化/平衡、同步与降级方案 | 研究如何被程序或现场执行 |
| 3. 运行产物 | 平台源文件、生成后的运行文件、环境版本、运行说明、设备与资源清单 | 另一个人能否启动同一实现 |
| 4. 数据接口 | 事件日志模式、稳定 ID、数据字典、缺失/排除规则、无真实被试的合成或烟雾数据 | 程序输出能否稳定进入分析 |
| 5. 分析与验证 | 目标软件分析契约、代码/模型接口、预期表图、语义审计、烟雾记录、差异账本、哈希 | 结果能否复核，跨文件是否一致 |

知情同意、debrief、支付、主试手册、多人同步、设备触发、隐私和异常处理不是所有任务都必须生成；论文设计一旦涉及，就属于必需产物而不是附加建议。

## 按复现层级选择最小交付

### 概念复现

必须：来源账本、理论/设计不变量、参与者流程、变量与指标、差异和验证计划。

不必默认生成：平台源文件、完整事件日志或可执行分析代码。

### 程序复现

必须：概念复现全部内容，加上平台对象图、材料、随机化、程序源文件、运行文件/生成状态、事件日志、数据字典、烟雾测试和实现差异。

### 统计复现

必须：数据来源与版本、导入契约、变量字典、排除、派生指标、模型/对比、表图映射、软件环境和结果差异。

不必默认生成：参与者界面或完整实验程序，除非它影响字段解释。

### 直接复制

必须：程序复现与统计复现的全部适用产物，并使用原作者允许使用的程序、材料、参数和分析包；任何替换都降级为程序复现或概念复现并记录差异。

## E-Prime 的最小程序复现包

1. `bundle_manifest.json`：统一 Study、Condition、Proc、List、关系与运行状态。
2. `procedure_map.csv`：逐 Proc 的对象时间线与日志责任。
3. `lists/*.tsv`：List 行、Procedure、TrialKind、Condition、Weight 和关键属性。
4. `eprime_build_spec.json`：E-Studio 对象、属性、设备、时序和生成步骤。
5. `inline/*.ebs`：必要且标明来源/用途的 E-Basic。
6. 材料与资源清单：文件名、许可、版本、哈希和使用位置。
7. `event_log_schema.json` 与 `data_dictionary.csv`。
8. `analysis_contract.json`：分析字段、派生变量和模型接口。
9. 用户创建的 `.es3` 与生成的 `.ebs3`；缺少时如实保持 `buildable`。
10. 烟雾测试记录、字段核对、语义审计和 SHA-256；全部通过后才是 `runtime-verified`。

## 其他平台的最小程序复现包

必须包含目标平台与版本、原生组件图、源文件/构建说明、条件与随机化、材料、事件或响应日志、稳定 ID、数据字典、分析契约、运行状态和验证测试。使用 `platform-adapters.md` 选择平台原生结构，并对结构化 JSON 运行 `scripts/validate_platform_plan.py`。

## 交付前问题

- 每个结论能回到来源吗？
- 每个参与者步骤能回到一个 Proc/对象或现场步骤吗？
- 每个非根 Proc 都有调用它的 List 吗？
- 每种重复关系是否被明确命名，而不是笼统写“循环/并行”？
- 每个程序输出字段都在数据字典里吗？
- 每个分析字段是直接记录还是声明了派生公式？
- 当前运行状态是否有相应产物证明？
